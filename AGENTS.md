# GuardDesk public-source development rules

Read `README.md`, `DEVELOPMENT-BASELINE.json`, `CURRENT-BASELINE.json`,
`doc/11-security-and-defender-guidelines.md` and
`doc/60-engineering-lessons-and-regression-rules.md` before making changes.

## Source and baseline

- Edit product code in `source/`, development tools in `dev/`, and documentation in `doc/`.
- `runtime/remote-next-src` is generated by `dev/worktree.py`; never edit it or overwrite developer changes there.
- The reference feature baseline is 0.4.105/001. This public snapshot has sanitized identifiers and documentation. Its bytes and acceptance status differ from internal historical binaries; do not claim otherwise.
- Preserve cumulative fixes, authorization, identity, policy, update/recovery/removal and remote-session behavior. Review adjacent regressions before changing shared code.
- Use `Build-Management.cmd` for complete packaging. Never patch historical recipes or combine unrelated EXE/DLL/cohort versions. Missing artifact evidence must stop packaging rather than become a fabricated pass.
- Never overwrite sealed outputs or automatically promote the reference baseline after a build.

## Development and testing

- Standard-account source editing, builds, static checks and the documented offline unit suite are allowed locally.
- Do not start a complete local/localhost management center, install an Agent, change OS protection, capture the real desktop or send OS input as an implicit test step. Integration needs an explicitly authorized external test environment.
- Default unit development may report the documented native-cohort fixture skip. Report it explicitly; a skipped test is not a pass. Full packaging requires its stronger gates.
- Native cache reuse must be explicitly selected and match source, receipt, log and artifact hashes. Say "reused" rather than claiming a fresh compile/runtime test.
- Do not run unfiltered discovery across all product tests or execute historical field-maintenance tools by default.
- Keep runtime, dist, private settings, databases, credentials, keys, diagnostics and binary artifacts out of commits.

## Security

- Use official Windows APIs and explicit, auditable elevation. SYSTEM must not run user-writable code or configuration.
- Process identity does not establish IPC object ownership. Keep the explicit SYSTEM owner/readback contract and client validation. Never accept a weaker owner to make a test pass.
- Preserve remote consent, roles, revocation, expiry, session/desktop generations and stale-input rejection.
- Do not disable Defender/EDR/AMSI/SmartScreen/UAC/App Control or execution policy; do not add exclusions, obfuscate or churn hashes to evade detection.
- Use verified TLS, bounded inputs/queues, parameterized SQL and protected credential storage. No arbitrary remote Shell or EXE deployment route.
- Publish only generic fixtures and documentation. Do not reintroduce customer/employer names, operational hosts/accounts, network topology, real device identities, internal repository locations or field evidence.
- Preserve third-party license texts and authors. Do not invent a first-party open-source license or imply formal certification.

## Evidence and delivery

Record relevant requirement/GD/SEC/DEF IDs, source/packaging boundaries, actual checks, evidence and unresolved gaps. Distinguish reported, hypothesized, reproduced, fixed, packaged, deployed and field-accepted states.
Unsigned or unaccepted builds remain internal candidates. No malware-detection guarantee, UAC/performance guarantee or production-readiness claim follows from compilation or a static scan.
